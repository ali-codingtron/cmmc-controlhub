Fix the Control HUB role and authorization architecture.

Current issue:
Control HUB currently has two competing role sources:

1. A global/legacy role selected when the user is initially created.
2. An organization-specific role assigned later under Edit User > Organization Access.

Example:

User:
JoeTest

Legacy/global role:
IT Contributor

Organization assignments:
- APEX Solutions — Compliance Manager
- Carme Tech — Organization Admin

Observed behavior:
- When JoeTest selects APEX Solutions and attempts to generate a document, the app says the user must be a Compliance Manager, even though JoeTest is a Compliance Manager for APEX Solutions.
- When JoeTest selects Carme Tech, Organization Admin functionality works correctly.

Likely cause:
The document-generation API or authorization middleware is checking User.role / globalRole instead of the user’s organization-specific membership role.

Goal:
Use organization-specific roles as the authoritative role for every organization-scoped action.

Do not change or delete production users, passwords, organization memberships, evidence, documents, controls, or other organization data.

====================================================================

Use two clearly separate concepts.

Platform role:

platform_role

- NONE
- GLOBAL_ADMIN

Allowed values:
- ORGANIZATION_ADMIN
- COMPLIANCE_MANAGER
- IT_CONTRIBUTOR

Do not use normal organization roles as global platform roles.

Do not store IT Contributor, Compliance Manager, Reviewer, or Organization Admin as a platform-wide role.

Global Admin is the only normal platform-wide role.

The break-glass system administrator should remain a Global Admin.

====================================================================

====================================================================
6. CENTRALIZE PERMISSION CHECKING
====================================================================

Create one centralized backend authorization service.

Example:

authorizeOrganizationAction(
  userId,
  organizationId,
  permission
)

Authorization order:

1. Load authenticated user.
2. If user.platform_role = GLOBAL_ADMIN:
   - allow according to Global Admin permissions.
3. Otherwise:
   - load the active OrganizationMembership for userId + organizationId.
4. Confirm membership exists and is Active.
5. Resolve the organization role.
6. Resolve permissions from the centralized permission matrix.
7. Allow or deny the requested action.

Do not use User.role or globalRole for organization-scoped permissions except GLOBAL_ADMIN.

Do not trust a role value sent by the frontend.

Do not rely only on hiding buttons.

Backend API routes must enforce authorization.

====================================================================

When a user switches organizations:

- resolve the user’s role for that organization

- refresh the UI permission context

Add endpoint or context similar to:

GET /api/auth/organization-context/:organizationId

Return:

- organization ID
- organization name
- effective role
- effective permissions
- membership status
- platform role

Example:

{
  "organizationId": "...",

  ]
}

The frontend may use this to show/hide controls, but the backend must still enforce permissions independently.

====================================================================

Check whether the login session or JWT stores one fixed role.

If it does, this causes incorrect behavior for users with different roles across organizations.

Do not store only:

in a session and use it for every organization.

Preferred:
- query active organization membership during authorization

If permission caching is required:
- cache per organization
- use a short expiration
- include an authorization version

- increment an authorization version
- make the new role effective immediately

JoeTest should not need to retain an old IT Contributor permission after being assigned Compliance Manager in APEX Solutions.
