Revise the Microsoft SSO implementation.

The current SSO Settings page is using the wrong architecture. It asks administrators to enter a separate Application Client ID, Tenant ID, Client Secret, and email domain for each organization.

I do not want each organization to create or configure its own Entra app registration.

Control HUB must use the single Control HUB-owned multi-tenant Microsoft Entra app registration whose credentials are already stored in Replit production secrets.

====================================================================
1. REMOVE THE SSO SETTINGS PAGE
====================================================================

Remove “SSO Settings” from the application sidebar.

Remove the organization-facing SSO configuration form that asks for:

- Application Client ID
- Directory Tenant ID
- Client Secret
- Email Domain

Remove or disable the route:

/sso-settings

Do not require organization administrators to configure Microsoft SSO.

Do not store Microsoft client secrets in the database.

Do not display or accept Microsoft client secrets through the Control HUB UI.

Microsoft SSO is a global platform authentication provider, not a separate app registration configured by each Control HUB organization.

====================================================================
2. USE THE GLOBAL REPLIT SECRETS
====================================================================

Use these production environment variables exclusively:

MICROSOFT_SSO_CLIENT_ID
MICROSOFT_SSO_CLIENT_SECRET
MICROSOFT_SSO_REDIRECT_URI
MICROSOFT_SSO_AUTHORITY
APP_BASE_URL

Expected production values:

MICROSOFT_SSO_REDIRECT_URI=https://controlhub.carmetechnology.com/api/auth/microsoft/callback

MICROSOFT_SSO_AUTHORITY=https://login.microsoftonline.com/organizations/v2.0

APP_BASE_URL=https://controlhub.carmetechnology.com

Do not fall back to a replit.dev preview URL in production.

Do not read SSO credentials from organization database records.

Do not expose MICROSOFT_SSO_CLIENT_SECRET to the browser, API responses, logs, or UI.

====================================================================
3. USE ONE CANONICAL CALLBACK ROUTE
====================================================================

Inspect the current implementation and identify the actual callback route.

Use one canonical production route:

/api/auth/microsoft/callback

The complete production redirect URI must be:

https://controlhub.carmetechnology.com/api/auth/microsoft/callback

Update all of the following to use this same URI:

- Microsoft authorization request
- OAuth callback handler
- environment variable validation
- production configuration
- login flow
- error handling

Do not use:

- temporary replit.dev URLs in production
- /api/auth/sso/callback in one location and /api/auth/microsoft/callback in another
- dynamically generated production callback URLs

If development testing requires a Replit preview callback, support it through a separate development environment variable:

MICROSOFT_SSO_DEV_REDIRECT_URI

Do not display the development callback to production users.

====================================================================
4. GLOBAL MICROSOFT SIGN-IN FLOW
====================================================================

The normal login page should show:

- Email
- Password
- Sign In
- Sign in with Microsoft
- Forgot Password

When the user clicks Sign in with Microsoft:

1. Create secure state, nonce, and PKCE values.
2. Store them securely server-side.
3. Redirect to Microsoft using the global multi-tenant app registration.
4. Use the organizations authority.
5. Request only the required sign-in scopes:
   - openid
   - profile
   - email
6. Microsoft authenticates the user.
7. Microsoft redirects to the canonical production callback.
8. Validate:
   - state
   - nonce
   - issuer
   - audience
   - expiration
   - token signature
9. Locate the existing Control HUB user.
10. Create a secure Control HUB session.

Microsoft authentication only proves identity.

Control HUB remains authoritative for:

- whether the user is allowed access
- user status
- organization assignments
- roles
- permissions
- assessor read-only restrictions
- Global Admin access

====================================================================
5. EXISTING USER MATCHING
====================================================================

Do not automatically create an authorized user after Microsoft login.

The user must already exist in Control HUB.

First Microsoft sign-in:

A. If the Control HUB user already has a stored Microsoft tenant ID and object ID:
- match using microsoft_tenant_id + microsoft_object_id

B. If the account is not linked yet:
- use normalized email only to find an existing active Control HUB user
- ensure exactly one user matches
- link the Microsoft tenant ID and Microsoft object ID
- preserve the user’s existing password
- preserve existing role
- preserve existing organization memberships
- preserve existing MFA configuration

C. If no existing user matches:
- deny access
- show:
  “Access has not been provisioned. Contact your Control HUB administrator.”

After initial linking, use the immutable Microsoft claims:

- tid
- oid

Do not use email, UPN, or email domain as the permanent identity key.

====================================================================
6. REMOVE EMAIL-DOMAIN AUTO-DETECTION DEPENDENCY
====================================================================

Do not require an organization administrator to configure an email domain before Microsoft login works.

The Sign in with Microsoft button should be globally available when Microsoft SSO is configured.

The user may enter their Microsoft account directly through Microsoft’s sign-in page.

If tenant restrictions are needed later, add a server-side organization tenant allowlist using Microsoft tenant IDs.

Do not use email domain alone as the security boundary.
