Implement secure sign-in and two-factor authentication for Control HUB while preserving all existing users, usernames, and passwords.

Important:
Do NOT reset existing passwords.
Do NOT force users to create new usernames.
Do NOT delete existing users.
Do NOT break the current login flow.
Do NOT require Microsoft SSO right now.

Keep the current local username/password login, but add MFA as a second step after the existing password is successfully verified.

Goal:
Existing users should continue logging in with their same current username/email and password. After password login, users should be prompted to enroll in or complete MFA depending on their role and MFA status.

1. Preserve Existing Accounts

Before changing authentication:
- inspect the current User model
- inspect the current password field/hash field
- inspect login flow
- inspect session handling
- inspect role and organization membership logic

Rules:
- keep all existing usernames/emails unchanged
- keep all existing passwords/password hashes unchanged
- do not invalidate existing accounts
- do not require bulk password reset
- do not migrate passwords unless absolutely necessary
- if password hashing is weak, report it first and propose a separate migration plan later

2. Add MFA Without Changing Passwords

Implement TOTP authenticator-app MFA.

Supported apps:
- Microsoft Authenticator
- Google Authenticator
- 1Password
- Bitwarden
- Authy
- any standard TOTP app

Login flow:
1. User enters existing username/email and password.
2. App verifies password using the existing logic.
3. If password is valid and MFA is required:
   - if user has MFA enrolled, prompt for 6-digit code.
   - if user has not enrolled, force MFA setup.
4. After valid MFA, create the app session.
5. If MFA is not required for that user yet, allow login normally.

3. MFA Enforcement Policy

Add an Admin setting:

Security Settings > MFA Enforcement

Options:
- Disabled
- Required for Admins only
- Required for privileged roles
- Required for all users

Default initial setting:
Required for Admins only

Privileged roles:
- Global Admin
- Organization Admin
- Compliance Manager
- Reviewer

Recommended final setting:
Required for all users

Assessor Read-Only should also require MFA once the organization is ready.

4. MFA Enrollment Flow

When MFA is required and the user has not enrolled:

Show page:
Set Up Two-Factor Authentication

Steps:
1. Display QR code.
2. Display manual setup key.
3. User scans QR code with authenticator app.
4. User enters 6-digit verification code.
5. App verifies code.
6. MFA is enabled.
7. Generate recovery codes.
8. Require user to copy/download recovery codes before continuing.

MFA setup should only happen after the existing password has been successfully verified.

5. Recovery Codes

Generate one-time recovery codes.

Requirements:
- generate 8 or 10 recovery codes
- store only hashed recovery codes
- show recovery codes only once
- allow user to download/copy them
- mark recovery code as used after successful login
- allow Admin to regenerate/reset MFA if user loses access

Recovery codes can be used instead of the authenticator code during MFA challenge.

8. MFA API Routes

Add backend routes:

POST /api/auth/login
- verifies existing username/password
- if MFA required, returns mfa_required state instead of creating final session
- if MFA not required, creates session

POST /api/auth/mfa/setup/start
- generates encrypted TOTP secret
- returns QR code URI and manual setup key

POST /api/auth/mfa/setup/verify
- verifies first TOTP code
- enables MFA
- generates recovery codes

POST /api/auth/mfa/verify
- verifies TOTP code during login
- creates final session if valid

POST /api/auth/mfa/recovery-code
- verifies one-time recovery code
- creates final session if valid
- marks recovery code as used

POST /api/auth/mfa/disable
- Admin only or user with password + MFA confirmation

POST /api/auth/mfa/reset
- Admin only
- resets user MFA enrollment
- requires reason
- logs audit event

POST /api/auth/logout
- destroys session

12. Session Security

Harden sessions.

Requirements:
- use server-side sessions or secure signed session cookies
- cookies must be HttpOnly
- cookies must be Secure in production
- cookies must use SameSite=Lax or Strict
- regenerate session ID after successful login
- destroy session on logout
- idle timeout
- absolute timeout
- revoke all sessions for user
- do not store tokens or session IDs in localStorage/sessionStorage

Suggested defaults:
- idle timeout: 30 minutes
- absolute timeout: 12 hours

13. Login Rate Limiting and Lockout

Add brute-force protection.

Rules:
- limit login attempts by account and IP
- after 5 failed attempts, lock account for 15 minutes
- show generic error:
  “Invalid username or password.”
- do not reveal whether the account exists
- audit log failed attempts
- show admin warning for repeated failures

MFA attempts:
- limit MFA attempts
- after repeated failed MFA attempts, require re-login
- audit log failed MFA attempts
